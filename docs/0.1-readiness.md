# 0.1 Readiness Gate

This document defines the focused release gate for treating the current tree as
a YuntaoCode 0.1 foundation candidate.

The gate is not a product roadmap, a benchmark, or a promise that every task
scenario is stable. It exists to answer one practical question:

> Is the local-first AI Task Runtime foundation coherent enough to stop adding
> new concepts and enter release hygiene?

## Boundary

The 0.1 readiness gate checks project facts. It does not participate in live
task execution and must not become another hidden planner or model-control
layer.

It should verify that:

- the product release version has one synchronized source;
- public documentation is UTF-8 without BOM or common mojibake markers;
- the foundation documents that describe Task, Context, Capability,
  Experience, Automation, Model Harness, and Desktop Observation exist;
- core runtime files compile;
- the current vanilla frontend files pass JavaScript syntax checks when Node.js
  is available;
- a focused runtime test subset passes;
- known local generated roots such as sidecar build environments, Tauri build
  output, and copied sidecar binaries are reviewed before tagging;
- changed source paths are covered by the 0.1 foundation inventory;
- dirty git state is visible before release tagging.

## Command

Run the default readiness gate:

```bash
python scripts/check_01_readiness.py
```

For a faster documentation and compile-only pass:

```bash
python scripts/check_01_readiness.py --skip-tests
```

For a stricter release-tagging pass:

```bash
python scripts/check_01_readiness.py --strict-js --strict-git
```

## Focused Test Set

The readiness script intentionally uses a focused test subset instead of the
entire suite. It covers the runtime surfaces that have recently become part of
the 0.1 foundation:

- user guidance during active runs;
- model transport harness behavior;
- read-only desktop observation provider contracts;
- run execution state;
- run finalization metadata;
- model/tool round streaming;
- advisory tool-result risks;
- capability preflight;
- context pack construction.

The full test suite is still valuable before publishing a tagged release:

```bash
pytest
```

## Interpretation

A passing readiness gate means the foundation has no obvious release-hygiene
blocker. It does not mean:

- every document, coding, browser, MCP, CLI, or desktop task is stable;
- every model provider behaves equally well;
- generated capability drafts are trusted runtime code;
- future extension directions are finished.

A readiness warning should be reviewed before tagging, but warnings are not
always blockers during normal development.

A readiness failure should block a 0.1 candidate until fixed.

The source groups that should enter the 0.1 foundation candidate are tracked in
[0.1-foundation-inventory.md](0.1-foundation-inventory.md).
