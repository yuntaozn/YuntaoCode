# 0.2 Development Direction

YuntaoCode `v0.1.0` is the first fixed public preview release. The `main`
branch now tracks `0.2.0-dev`.

This document is not a product roadmap and not a promise that a feature will
ship in 0.2. It is a direction guard for deciding what belongs in the main
runtime after 0.1.

## Version Boundary

- `v0.1.0` remains the fixed public preview tag.
- `0.1.x` is reserved for clear fixes to the published installer or released
  source.
- `0.2.0-dev` is the main development line for the next foundation work.

## 0.2 Theme

0.2 focuses on:

- **Observation Runtime**: make task execution and produced state observable.
- **Verification Runtime**: let the model judge completion from concrete
  evidence instead of relying on unsupported summaries.
- **Artifact Runtime**: make task outputs explicit, typed, inspectable, and
  reusable by later runtime layers.

The goal is not to add more scenarios by default. The goal is to make the
runtime better at seeing what happened, preserving evidence, and exposing the
right facts back to the model and the user.

## Direction Checks

A mainline 0.2 change should answer at least one of these questions:

- Does it give the model or user better evidence about current task state?
- Does it improve how a Run records produced artifacts, logs, previews,
  screenshots, diagnostics, or validation facts?
- Does it help the model detect that a task is incomplete and choose a new safe
  strategy?
- Does it reduce hidden runtime conclusions, fixed routes, or task-specific
  branching?
- Does it keep MCP, CLI, built-in tools, and future plugins inside the same
  Capability Runtime boundary?

If a change only adds a scenario, marketplace concept, provider list, or
product promise, it should start in a service branch, plugin, or Capability Pack
until real runs show which runtime boundary it improves.

## Suitable 0.2 Work

Examples of work that fits the direction:

- capture browser, file, desktop, process, and external-application observations
  as evidence records;
- connect visual evidence and text diagnostics to RunResult without making the
  runtime decide the final answer;
- feed model-declared route evidence back into completion self-review so the
  model can see capability fit, route gaps, and verification facts together;
- represent outputs as artifacts with roles such as `draft`, `final`,
  `preview`, `screenshot`, `log`, `backup`, or `diagnostic`;
- improve long-task progress, heartbeats, partial artifacts, and continuation
  evidence;
- make provider health and tool-result facts clearer without blocking safe model
  self-correction.

Examples that should stay outside mainline until proven:

- a full video generation product;
- a courseware-specific assistant;
- a document-agent workflow that hard-codes one domain process;
- a plugin marketplace;
- automatic promotion of AI-generated tool code into the trusted runtime.

These can still be explored in dedicated branches or packages. The mainline
should absorb only the reusable runtime contracts that real task evidence
justifies.
